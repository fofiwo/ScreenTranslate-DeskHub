# 截图首次使用性能优化

日期：2026-11-11。

## 结论与范围

用户补充后，本轮目标以“首次明显卡顿、第二次流畅”为主。现场连续两次截图均成功，因此早期观察到的微信输入法改写剪贴板不能认定为原故障根因。其他电脑“流程完成但无结果”尚未复现，不能宣布已修复。

合成图片测试确认存在冷启动开销。先前约 317–339ms 的窗口构造样本来自尚未构造主界面的独立进程，不能当作日常程序已启动后的首次截图延迟。对抗复核补充了先构造、布局主界面的条件：单次样本中首次截图构造约 28.4ms → 5.7ms，注入回调的复制流程约 28.8ms → 14.7ms；仍不包含真实屏幕呈现及系统剪贴板操作。原先的独立进程数据保留在下表供追溯。

## 实施

原现场已有另一项任务加入的 ShortcutUiWarmup 与 App 启动调用；本轮在其基础上仅扩展截图部分：

1. 将截图预加载排在资料库和剪贴板窗口准备之前，避免其等待其他存储加载；通过既有 ApplicationIdle 与捕获中跳过条件执行。
2. 用 32×32 合成位图预备 GDI→WPF 转换，再完成截图控件的离屏布局。
3. 用 2×2 合成像素在 STA 工作线程预备本地图像数据对象、RGB 比较和 PNG 编码；不发布到系统剪贴板、不读取用户内容、不捕获桌面、不生成可见窗口。
4. RunStaAsync 在线程池启动 STA，并让线程调度及收尾不依赖调用方的 UI SynchronizationContext；实际图片工作和异步重试仍在 STA 消息泵中执行，完成或失败后线程退出。
5. 截图复制记录尺寸、耗时、异常类型和 HRESULT。日志不包含像素、文字或原始异常内容。保留写后逐像素比较、串行写入、占用重试、取消和失败保留选区。
